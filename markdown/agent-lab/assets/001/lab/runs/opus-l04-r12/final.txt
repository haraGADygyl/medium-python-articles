`mypy` now passes in strict mode. `ruff check` is clean and all 48 tests pass. I didn't use `# type: ignore`, `cast` or `Any`, and didn't touch the mypy config.

**What was wrong:** `Point.ele` is `float | None`, because a point can be missing its elevation where the GPS lost it. But the ascent/descent, highest/lowest, steepest-grade and walking-time code all treated it as a plain `float`. So these weren't just typing complaints: a track with an empty elevation would have crashed with a `TypeError` at runtime.

**The fix:**
- **`src/trailhead/track.py`**: I added `Track.elevations() -> list[float]`. It fills each gap using the rule the README already describes: a missing point takes the elevation of the nearest earlier point that has one, or, if none does, the nearest later one. `Point.ele` itself stays `None`, as the README says.
- **`elevation.py`, `pace.py`, `report.py`**: these now call `track.elevations()` instead of reading `point.ele` directly.

**One thing for you to decide:** the README doesn't say what to do with a track where no point has an elevation at all. I made `elevations()` raise `TrackError("the track has no elevations")`. Before, the CLI only caught `TrackError` while loading the file. So in `cli.py` I moved the summary and plan calls inside that `try`, which makes the CLI print a normal `trailhead: …` error instead of a traceback. If you'd rather reject such files when they're parsed, or treat them as flat, that's a small change.

I checked by hand that a track with a gap at the start and one in the middle fills to `[100, 100, 100, 130]` and summarises correctly. I didn't add tests for filling gaps or for a track with no elevations; I can if you want them.
