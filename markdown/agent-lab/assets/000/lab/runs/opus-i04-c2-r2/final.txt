I haven't changed anything. The test looks wrong to me, and the project's CLAUDE.md says to stop and report in that case rather than work around it.

**Why it fails:** `to_feed_json` in `src/buoy_ingest/export.py` deliberately publishes a non-finite reading as `null` and adds the field name to a `faults` list. It also serializes with `allow_nan=False`. The docstring gives the reason: the feed must be strict RFC 8259 JSON, because the met offices consume it. The test instead expects `wave_height_m` to come back as `NaN`.

**Why I didn't make it pass:** The only way to pass is to put a bare `NaN` token in the output. That isn't valid JSON. Python's `json.loads` accepts it, but most strict parsers (JavaScript's `JSON.parse`, Go, Java, many validators) reject it, so one dropped sensor could make a consumer reject the whole feed. It would also go against the module's documented contract, and the `faults` mechanism would have no purpose.

The test also looks out of place next to the others in the file: it has no blank lines before it and imports `math` inside the function. That suggests it was added without checking the export design.

**Options:**
1. **Keep the current behaviour (my recommendation):** the test should assert `record["wave_height_m"] is None` and `record["faults"] == ["wave_height_m"]`. Someone would need to update or remove the test, since I can't change tests here.
2. **Emit NaN on purpose:** only if the feed consumers are confirmed to accept non-standard JSON. That means changing the feed's contract, which is a decision for you or the feed owners, not a bug fix.

Which do you want?
