**What the test wants:** `test_every_attempt_uses_a_fresh_key` sets up a server that applies the batch and then times out, lets the uploader retry, and asserts `len(server.applied) == 2`. That means each retry has to send a new idempotency key, and the server ends up applying the same batch twice.

**What the README and docstrings say:**
- README, *Uploads*: "A retried batch carries the same idempotency key, so the feed server applies it once."
- `Uploader` docstring (`src/buoy_ingest/uploader.py:23-28`): "A retry must reuse the batch's idempotency key: the server may already have applied an attempt that timed out, and the key is how it recognises the resend."
- `send_chunked` docstring: "...every chunk is applied exactly once and a retried chunk reuses its key."
- `UploadTimeout` docstring: the server "may or may not have applied the batch". This is exactly the case the test builds with `apply_before_timeout=True`.

**Why it matters:** the current code creates one key per batch and reuses it on every retry, which is what the docs describe, so the server applies the batch once. To pass the test I'd have to make a new key per attempt. Then any timeout that happens after the server has already applied the batch would publish duplicate records to the met-office feed, which is the problem idempotency keys exist to prevent. The other four tests in the file pass, and `test_send_retries_after_a_lost_request` checks that exactly one record is applied.
