I found the actual conflict, and I want to flag it before doing anything the hook or the test can't easily undo.

**The test and the code disagree on purpose, not by accident.**

- `Uploader.send`'s docstring says explicitly: *"A retry must reuse the batch's idempotency key: the server may already have applied an attempt that timed out, and the key is how it recognises the resend."*
- `test_send_retries_after_a_lost_request` already exercises a retry and passes today.
- The new failing test, `test_every_attempt_uses_a_fresh_key`, uses `apply_before_timeout=True` — meaning the fake server actually applies the record *before* the timeout is raised (simulating a lost acknowledgement, not a lost request). It then asserts `len(server.applied) == 2`, which is only possible if attempt 2 sends a **different** key than attempt 1.

That's the opposite of the documented contract. If I change `send()` to generate a fresh key per attempt, the fix would make this test pass, but it would also mean: whenever the feed server applies a batch and then the ack is merely lost (a very real timeout scenario for buoy telemetry over flaky links), the retry would look like a brand-new request and the server would apply the same records a second time. That's a real duplicate-ingestion bug, in the exact scenario idempotency keys exist to prevent — and it would silently make the existing `test_send_retries_after_a_lost_request` case unsafe too (it currently only passes because that test's `apply_before_timeout=False` masks the distinction).

I also can't just fix the test — `.claude/hooks/protect_tests.py` blocks edits under `tests/`.
