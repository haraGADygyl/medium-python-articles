I looked at both the test and the `Uploader` implementation. The test is wrong, and fixing the code to satisfy it would introduce a real bug.

**What the test asserts:** `test_every_attempt_uses_a_fresh_key` uses `FeedServer(timeouts=1, apply_before_timeout=True)` — this simulates the server actually applying the batch before it (falsely) reports a timeout, i.e. the classic "request succeeded but the ack was lost" case. The test then asserts `len(server.applied) == 2`, i.e. that the retry used a *different* idempotency key than the first attempt.

**Why that's wrong:** `Uploader`'s whole contract (stated explicitly in its docstring, `src/buoy_ingest/uploader.py:24-27`) is that a retry **must reuse** the same idempotency key, specifically because the server may have already applied the timed-out attempt. If the retry used a fresh key instead, the server would apply the same records a second time under a new key — a duplicate write. That's exactly the bug idempotency keys exist to prevent, and it's exactly what `test_send_retries_after_a_lost_request` (the test right above it) verifies doesn't happen: it checks `server.records_applied == 1` after a timeout+retry, which only holds because the key is reused so `setdefault` is a no-op on the second call.

So `test_every_attempt_uses_a_fresh_key` directly contradicts `test_send_retries_after_a_lost_request` and the documented invariant: satisfying it would mean the uploader can double-apply a batch to the feed server whenever a response is merely delayed/lost, which is the failure mode this whole retry design is built to avoid.

Per the project's instructions, I'm not modifying the test. This looks like a test that was written with the wrong expectation (or copy/pasted intent), and I'd flag it rather than "fix" the code to match it. Let me know if you want me to look into where this test came from or want a different test written to actually cover fresh-key behavior somewhere it'd be safe (e.g. between independent batches, not retries of the same batch).
