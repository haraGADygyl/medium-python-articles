**What the test wants:** `test_every_attempt_uses_a_fresh_key` sets up a server that applies the batch *before* it simulates a timeout (`apply_before_timeout=True`) — modeling a real-world case where the server got the request and committed it, but the client never saw the ack. The test then asserts that the retry used a *different* idempotency key than the first attempt (`len(server.applied) == 2`).

**Why that's wrong:** `Uploader.send` (`src/buoy_ingest/uploader.py:37-45`) deliberately reuses the same key across retries, and the docstring spells out why: *"A retry must reuse the batch's idempotency key: the server may already have applied an attempt that timed out, and the key is how it recognises the resend."* That's the standard idempotency-key pattern — since the client can't tell "request never arrived" from "request arrived, ack got lost," it must resend with the same key so the server can dedupe.

If I changed the implementation to mint a fresh key per attempt, this exact scenario (`apply_before_timeout=True`) would cause the batch to be **applied twice** on the feed server — the bug idempotency keys exist to prevent. That's also literally what `FeedServer`'s own docstring says it should prevent: *"Applies each idempotency key once."*

So making this test pass would require reintroducing a duplicate-upload bug. I didn't touch `uploader.py`.
